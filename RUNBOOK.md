# Эксплуатация

Документ для того, кто дежурит, а не для того, кто писал код. Порядок такой:
сначала что делать прямо сейчас, потом почему.

## Развернуть с нуля

```bash
make up          # поднять PostgreSQL и RabbitMQ
make migrate     # накатить схему
make seed        # завести склады
make run         # веб-процесс
make worker      # отправщик из очереди в брокер, во втором окне
make consumer    # приёмник из брокера, в третьем
```

Приёмник запускается обязательно, а не по желанию: топологию очередей
объявляет он, и до его первого запуска сообщения для этой цели брокеру
некуда класть.

Проверка: `curl localhost:8000/health` отвечает `{"status":"ok","database":"ok",...}`.
Документация ручек: `localhost:8000/docs`. Очереди брокера:
`localhost:15672`, вход `stocksync` / `stocksync`.

## Первое, что надо посмотреть при жалобе

```bash
curl -s localhost:8000/health         # база жива, размер очереди, мёртвые события
curl -s localhost:8000/v1/outbox      # разбивка очереди по состояниям
```

| Что видно | Что это значит | Что делать |
|---|---|---|
| `status: ok`, `pending_events` близко к нулю | всё в порядке | ничего |
| `pending_events` растёт, `dead_events` = 0 | приёмник отвечает медленно или воркер не запущен | проверить, жив ли процесс воркера |
| `dead_events` больше нуля | события исчерпали попытки | см. «Мёртвая очередь» |
| ответ 503 | база недоступна | см. «База недоступна» |
| очередь пуста, а приёмник ничего не получает | сообщения не доходят до очереди в брокере | см. «Брокер недоступен» и «Сообщения возвращаются» |

Здоровье проверяется настоящим запросом в базу, а не строкой «ok». Сервис,
который отвечает «ok» не касаясь базы, продолжает делать это и после того,
как база отвалилась, и балансировщик такой узел не выключит.

## Очередь растёт

1. Жив ли воркер: `docker compose ps worker` или `ps aux | grep app.worker`.
2. Если жив, посмотреть, на чём он спотыкается:
   ```sql
   SELECT target, count(*), max(last_error)
   FROM outbox WHERE status = 'failed' GROUP BY target;
   ```
3. Одна цель лежит, вторая работает — это нормальная картина, сервис
   продолжает доставлять во вторую. Ждать восстановления первой.
4. Обе цели молчат — проблема на нашей стороне сети, а не у приёмников.

Очередь в базе переживает перезапуск и веб-процесса, и воркера. Терять
события при выкате она не может, поэтому «перезапустить и посмотреть»
здесь безопасно.

## Мёртвая очередь

Событие уходит в неё после того, как исчерпало все попытки. Это отдельное
состояние, а не «просто не доставлено»: такие события требуют человека, а
не очередного повтора.

```sql
SELECT id, target, attempts, last_error, created_at
FROM outbox WHERE status = 'dead' ORDER BY id LIMIT 20;
```

Сначала чинится причина (доступ, адрес приёмника, формат тела), и только
потом события возвращаются в очередь:

```bash
curl -X POST localhost:8000/v1/outbox/revive
```

Счётчик попыток при этом обнуляется, иначе событие уйдёт в мёртвые с
первой же неудачи.

## Брокер недоступен

Признак: в логе воркера повторяются ошибки соединения, `pending_events`
растёт, а `dead_events` пока нет.

```bash
docker compose ps rabbit
docker compose logs --tail=50 rabbit
curl -s -u stocksync:stocksync localhost:15672/api/overview | head -c 200
```

Ничего чинить в сервисе не нужно. Событие остаётся в очереди в базе, воркер
повторяет попытки с растущей паузой и подхватит всё, как только брокер
поднимется. Проверить после подъёма: `pending_events` идёт вниз.

Если брокер лежит дольше, чем `delivery_attempts` попыток, события уйдут в
мёртвую очередь. Это не потеря: их возвращает `POST /v1/outbox/revive`
после того, как брокер поднялся.

## Сообщения возвращаются

Признак: в `last_error` событий стоит `Unrouted` со словами «нет подходящей
очереди».

Значит, под ключ маршрутизации `stock.<цель>` не привязана ни одна очередь:
приёмник для этой цели не запущен ни разу. Обменник без привязки молча
выбросил бы сообщение, поэтому издатель ставит флаг `mandatory` и считает
возврат неудачей.

```bash
# какие очереди существуют и сколько в них сообщений
docker compose exec rabbit rabbitmqctl list_queues name messages consumers
```

Лечится запуском приёмника: топологию объявляет он, а не издатель.

```bash
docker compose up -d consumer          # или: python -m app.consumer --target ozon
curl -X POST localhost:8000/v1/outbox/revive
```

## Мёртвая очередь в брокере

Отдельно от мёртвой очереди в базе. В базу попадает то, что не удалось
отправить, в брокер то, что приёмник отверг: не разобралось как JSON или
пришло без `message_id`.

```bash
docker compose exec rabbit rabbitmqctl list_queues name messages | grep '\.dead'
```

Посмотреть тела, не вынимая их из очереди, проще всего в панели на
`localhost:15672`, вкладка Queues, кнопка Get messages с режимом
`Nack message requeue true`.

Повторная обработка требует человека: если тело не разбирается, его
возврат в основную очередь ничего не изменит.

## Приёмник получил одно и то же дважды

Это штатный ход событий, а не сбой: RabbitMQ обещает доставку не реже
одного раза, и приёмник, упавший между обработкой и подтверждением,
получит сообщение снова.

Повтор отсеивается таблицей `inbox` по `message_id`. Проверить, что отсев
работает:

```sql
SELECT message_id, target, received_at FROM inbox ORDER BY received_at DESC LIMIT 20;
```

В логе приёмника такой случай виден строкой «сообщение N уже обработано,
повтор пропущен».

## Остаток уехал не туда

```bash
# что происходило с артикулом
curl -s "localhost:8000/v1/changes?sku=ART-0042"

# откатить всю партию целиком
curl -X POST localhost:8000/v1/batches/<batch_id>/revert
```

Откат возвращает каждой строке значение, которое было до правки, пишет об
этом в журнал и ставит событие для внешних систем. Правки откатываются в
обратном порядке: если строка в одной партии менялась дважды, откат в
прямом порядке вернул бы промежуточное значение.

Если строки до партии не существовало, откат ставит ноль, а не удаляет
запись: на неё уже могли сослаться.

## База недоступна

1. `docker compose ps db`, `docker compose logs --tail 50 db`.
2. Проверить, не кончилось ли место: `df -h`. Это самая частая причина.
3. Веб-процесс переживёт недоступность базы и ответит 503, воркер будет
   ждать. Перезапускать их не нужно: соединения поднимаются сами
   (`pool_pre_ping` проверяет соединение перед каждым использованием).

## Правки от площадки приходят дважды

Так и задумано. Площадка при таймауте повторяет вебхук, и повтор с тем же
заголовком `Idempotency-Key` не двигает остаток второй раз, а возвращает
прежний ответ с заголовком `Idempotent-Replay: true`.

Если площадка шлёт один и тот же ключ с разным телом, сервис отвечает 409.
Это ошибка на её стороне, и прятать её, молча возвращая старый ответ,
нельзя.

Ключи живут сутки и убираются по расписанию:

```bash
curl -X POST localhost:8000/v1/maintenance/purge-idempotency
```

## Выкат новой версии

1. `python -m alembic upgrade head` до перезапуска приложения.
2. Перезапустить веб-процесс. Незавершённые отправки не теряются: они
   лежат в базе, а не в памяти процесса.
3. Перезапустить воркер.
4. Проверить `/health` и `/v1/outbox`.

Откат выката: `python -m alembic downgrade -1`, затем предыдущий образ.
Каждая миграция обязана иметь работающий `downgrade`, это проверяется
тестом и сборкой.

## Чего сервис не делает

- Не хранит историю остатков по дням. Журнал изменений это не витрина
  данных: он отвечает на вопрос «кто и когда поменял», а не «сколько было
  во вторник».
- Не разрешает конфликты между площадками. Источник правды один, и это
  наш склад.
- Не гарантирует порядок доставки событий между разными артикулами. Внутри
  одного артикула порядок сохраняется на отправке, потому что события
  выбираются по возрастанию идентификатора. После брокера порядок между
  несколькими приёмниками одной очереди не гарантируется вовсе: если он
  нужен, очередь придётся читать одним приёмником.
- Не чистит таблицу inbox. Она растёт линейно по числу принятых сообщений,
  и на длинной дистанции ей нужен срок хранения, как и ключам
  идемпотентности.
